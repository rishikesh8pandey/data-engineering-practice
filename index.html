The idea

Every problem is built around a trap

A trap is something in the data that makes a reasonable-looking query return the wrong answer, usually without an error. Pick the one that keeps catching you.

NULL trap13 problemsA comparison with NULL is never true, and never false either. Fan-out trap4 problemsA join or an explode repeats rows, and the sums grow. Tie trap5 problemsTwo rows sort as equal, and which one wins is left to chance. Boundary trap14 problemsThe first day, the last second, the exact cut-off. Duplicate trap5 problemsThe same row arrives twice. Late-data trap3 problemsData that turns up after you stopped looking for it. Schema trap4 problemsColumns that are not what their name, type or position suggests. Grain trap3 problemsA number worked out at one level and reused at another.

How it works

From problem to explanation in four steps

  1. Pick a problem

    Filter by trap, track or difficulty. Every problem comes with a small dataset that has the awkward rows planted on purpose.

  2. Write your answer

    SQL problems have an editor on the page. Every problem also has a Google Colab notebook that installs PySpark and loads the data.

  3. Run the check

    It tells you what kind of thing is wrong (a missing column, the row count, which column) and never shows the answer.

  4. Read the explanation

    The approach, the common wrong answers and why each one fails, with the real numbers from the data.

Who it is for

Freshers and working engineers

NullTrap is for people in India preparing for data engineering interviews, and for engineers who want to get better at the work itself. The problems use small synthetic datasets with the awkward cases planted on purpose: nulls, ties, duplicates, late records.

The problems listed here are free. Harder problems with detailed explanations will be paid later.

About

Why it exists

NullTrap is built by Rishikesh Pandey, a data engineer who works with PySpark, Databricks and Delta Lake.

Most practice sites test whether you can write a query. In a real pipeline the query is rarely the hard part. The data is: the NULL in a lookup table, the payment that arrives twice, the event that shows up two days late.

It is a one-person side project. If something is wrong or unclear, open an issue on GitHub.
